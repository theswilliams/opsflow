# n8n integration

OpsFlow exposes a small, signed HTTP API so an orchestrator such as n8n can hand it work and wait for the human decision.

```text
n8n Webhook / Email trigger
   → Sign request (Code)
   → POST /api/webhooks/workflow        OpsFlow: durable job → AI extraction → validation → REVIEW_REQUIRED
   → Wait (30 s)
   → Sign status request (Code)
   → GET  /api/webhooks/workflow/:id     … a person reviews and approves in OpsFlow …
   → Switch on status
        COMPLETED → notify with `confirmation`
        REJECTED  → notify rejected
        FAILED    → alert with `failure_reason`
        (other)   → back to Wait
```

## 1. Create a credential

In OpsFlow open **Integrations → Webhook credentials → Create credential**. Copy the **Key ID** and **secret** — the secret is shown once and stored encrypted. A user may hold at most 5 active credentials (revoke one to make room). `npm run db:seed` also prints a demo credential.

## 2. Configure n8n

Set these environment variables for n8n (never paste the secret into a node):

| Variable | Value |
| --- | --- |
| `OPSFLOW_URL` | e.g. `http://localhost:3000` (no trailing slash) |
| `OPSFLOW_KEY_ID` | `ofk_…` |
| `OPSFLOW_SECRET` | `ofs_…` |
| `NODE_FUNCTION_ALLOW_BUILTIN` | `crypto` (the Code nodes use Node's `crypto`) |
| `N8N_BLOCK_ENV_ACCESS_IN_NODE` | `false` (allows `$env` in nodes) |

Import [`n8n/opsflow-workflow.json`](../n8n/opsflow-workflow.json) (Workflows → Import from file). Replace the three placeholder notification nodes with Slack/Email/SMS. To test end-to-end, POST to the n8n webhook `/webhook/opsflow-intake` with `{"text": "Customer: ABC…"}`, then open the workflow in OpsFlow and approve it.

> The importable JSON is generated by `scripts/build-n8n-workflow.mjs`. It has been validated structurally and its signing code is executed in the test-suite against the real handler (`tests/n8n-workflow.test.ts`, including repeated triggers), but it has **not** been imported into a running n8n instance. Node parameter formats can differ between n8n versions; if an import complains, the two Code nodes and the request headers below are the parts that matter.

### Stable idempotency (repeated triggers)

The **Sign request** node sets `external_id` to, in order: the upstream `external_id`, the upstream `message_id` (e.g. an email Message-ID), or a hash of the message text. It is **not** derived from the n8n execution id (which changes on every run, so a re-triggered flow used to create a duplicate). A repeated trigger for the same message therefore returns the *original* workflow (`200`, `duplicate: true`). Consequence to know: two genuinely different orders with byte-identical text and no upstream id are treated as one; give the flow a real message id if that matters. Ids must match `[A-Za-z0-9_.:@-]{1,200}` (so strip `<`/`>` from a raw Message-ID).

## 3. The API

### Signing (scheme v1)

Every request carries:

| Header | Value |
| --- | --- |
| `X-OpsFlow-Key-Id` | your key id |
| `X-OpsFlow-Timestamp` | Unix time in seconds |
| `X-OpsFlow-Signature` | `sha256=` + hex `HMAC-SHA256(secret, message)` |
| `Idempotency-Key` | optional; **covered by the signature** |

`message` is four parts joined by a single line-feed (`0x0A`): the literal `v1`, the timestamp, the idempotency key (empty string if you send none), and the **raw request body**:

```text
v1 LF <timestamp> LF <idempotency-key or empty> LF <raw body>
```

Sign the **exact bytes** you send (in n8n: HTTP Request → Body Content Type *Raw*, `application/json`, body from the Code node). For `GET`, the idempotency key and body are both empty (`v1 LF <timestamp> LF LF`). The timestamp must be at most 5 minutes old and at most 60 seconds in the future. Because the idempotency key is inside the signature, changing it invalidates the request — a captured request cannot be replayed under another key.

```bash
BODY='{"type":"delivery_request","text":"Customer: ABC\n4 pallets of shingles to 125 King Street, London, Ontario this Friday","external_id":"order-1042"}'
TS=$(date +%s)
SIG=$(printf 'v1\n%s\n\n%s' "$TS" "$BODY" | openssl dgst -sha256 -hmac "$OPSFLOW_SECRET" | sed 's/^.* //')
curl -X POST "$OPSFLOW_URL/api/webhooks/workflow" \
  -H "Content-Type: application/json" \
  -H "X-OpsFlow-Key-Id: $OPSFLOW_KEY_ID" -H "X-OpsFlow-Timestamp: $TS" -H "X-OpsFlow-Signature: sha256=$SIG" \
  -d "$BODY"
```

Or use the helper: `OPSFLOW_KEY_ID=… OPSFLOW_SECRET=… node scripts/send-webhook.mjs http://localhost:3000`, and `node scripts/verify-audit-fixes.mjs` (with `--proxied`, and the server started with `TRUSTED_PROXIES=127.0.0.1,::1`, for the client-isolation checks) to re-run the replay / rate-limit exploits against a running server.

### `POST /api/webhooks/workflow`

Body (strict — unknown fields are rejected):

```json
{ "type": "delivery_request", "text": "…up to 20,000 chars…", "external_id": "order-1042" }
```

Success — `201` (new) or `200` (`duplicate: true`, the original workflow returned):

```json
{
  "id": "cmu…",
  "status": "REVIEW_REQUIRED",
  "needs_attention": true,
  "duplicate": false,
  "failure_reason": null,
  "review_url": "http://localhost:3000/workflows/cmu…"
}
```

Processing is a **durable background job**. The request gives it a short head start (up to ~25 s), so with the mock provider — or a fast model — the response already carries `REVIEW_REQUIRED`. If extraction takes longer, `status` is `RECEIVED` or `PROCESSING` and the job continues on the server (with retries and crash recovery); poll the `GET` endpoint. A `FAILED` status carries a generic `failure_reason` and can be retried in the UI. **Never assume the response is final: always poll.**

### `GET /api/webhooks/workflow/:id`

```json
{
  "id": "cmu…", "status": "COMPLETED", "needs_attention": false, "decision": "approved",
  "failure_reason": null, "updated_at": "2026-09-25T10:02:23.000Z",
  "data": { "customer": "…", "address": "…", "requested_date": "2026-10-02", "…": "…" },
  "confirmation": { "subject": "…", "body": "…" }
}
```

`data` (the frozen, **approved** fields) is `null` until a person has approved; `confirmation` is set after the action succeeded. A workflow that belongs to another account is `404`.

### Errors

| Status | `error.code` | Meaning |
| --- | --- | --- |
| 400 | `invalid_json` / `invalid_payload` / `invalid_idempotency_key` | Malformed body; `issues[]` lists field paths |
| 401 | `unauthorized` | Missing/unknown key, bad signature, stale or future timestamp (deliberately indistinguishable) |
| 404 | `not_found` | Unknown id, or not yours |
| 409 | `idempotency_conflict` | Key reused with a different payload |
| 413 | `payload_too_large` | Body over 64 KiB |
| 415 | `unsupported_media_type` | Not `application/json` |
| 429 | `rate_limited` | Honour `Retry-After` |
| 500/503 | `internal_error` / `service_unavailable` | Generic; quote the `x-request-id` header |

Limits: 64 KiB body; 60 requests/min per credential **and** 120/min per account across all its credentials (configurable); failed signatures are throttled per client address only, so nobody can lock your credential out by guessing at its public key id.

## Design notes

- **Polling instead of callbacks.** Accepting a callback URL would create an SSRF surface. Polling a signed `GET` needs no outbound requests from OpsFlow.
- **Approval stays in OpsFlow.** n8n can never approve; it only observes the decision. The reviewed `data` is released only after approval, as the frozen snapshot that was approved.
- **Loop guard.** The workflow's `executionTimeout` is 48 h; add a max-iterations counter if you need a tighter bound.
